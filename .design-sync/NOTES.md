# design-sync notes — salas-reuniao-fullstack (components/ui)

## Repo shape

This repo is a Next.js 15 app, not a published component package. `components/ui/`
is a standard shadcn/ui set (Radix primitives + `class-variance-authority` +
`tailwind-merge`), used directly as app source — there is no `dist/`, no `.d.ts`
build, no Storybook.

To sync it as a "package" shape design system:
- `cfg.pkg = "salas-reuniao-ui"` is a synthetic package name — it does not exist
  on npm. A Windows directory **junction** at `node_modules/salas-reuniao-ui`
  pointing back at the repo root makes `PKG_DIR = join(NODE_MODULES, PKG)`
  resolve to the repo, so the converter's default (no `--entry`) synth-entry
  path triggers: it scans `cfg.srcDir` (`components/ui`) for PascalCase value
  exports via `deriveComponentsFromSrc`. This picked up all 122 named exports
  (Button, Card, CardHeader, DialogContent, etc.) with zero manual
  `componentSrcMap` entries.
  - Recreate the junction on a fresh clone: `New-Item -ItemType Junction -Path node_modules\salas-reuniao-ui -Target .` (PowerShell) before re-running the converter.
  - Do NOT pass `--entry` — that disables the synth-entry / `deriveComponentsFromSrc` fallback entirely (falls back to `.d.ts`-only discovery, which finds nothing here).

## Critical fix: cssEntry must be COMPILED Tailwind, not raw globals.css

`app/globals.css` only contains `@tailwind base/components/utilities;` directives
— those are meaningless to a browser until run through PostCSS/Tailwind CLI.
Pointing `cssEntry` straight at `app/globals.css` (the naive default) ships a
stylesheet with **zero actual utility classes** — every component preview
rendered as unstyled native HTML (no color, no radius, no padding) even though
render-check reported no errors. This is silent and easy to miss without
actually looking at a screenshot.

Fix: `cfg.cssEntry` points at `.design-sync/compiled-tailwind.css`, and
`cfg.buildCmd` runs Tailwind CLI to (re)generate it before every build:

```
npx tailwindcss -i app/globals.css -o .design-sync/compiled-tailwind.css --config tailwind.config.mjs
```

The compiled file is gitignored (build artifact, regenerated by `buildCmd`).
**Always re-run `buildCmd` before `package-build.mjs` on every sync** —
otherwise you'll ship a stale or (on a truly fresh clone) missing CSS file.

**Also hits `SidebarMenuSkeleton`**: it composes `<Skeleton>` internally, so its loading
placeholder rows are invisible for the same reason — confirmed in the preview capture
(both cells show real content but zero visible skeleton bars). Same root cause, not a
separate bug; graded `needs-work` in `SidebarMenuSkeleton.grade.json`.

## Styling idiom

Tailwind v3 (not v4) with CSS-variable-backed tokens (`oklch(...)` values) in
`app/globals.css` `:root`/`.dark`, consumed via `tailwind.config.mjs`
`theme.extend.colors` (e.g. `bg-primary` → `var(--primary)`). Utility classes
composed with `class-variance-authority` (cva) + `cn()` (`clsx` + `tailwind-merge`,
in `lib/utils.ts`). No component-scoped CSS files — all styling is Tailwind
utility classes in the `.tsx` `className` props.

## Real app bug found: DropdownMenuItem's `variant="destructive"` renders invisible text

Not a design-sync artifact — a genuine bug in `components/ui/dropdown-menu.tsx` worth
fixing in the app itself. `data-[variant=destructive]:text-destructive-foreground` is
applied unconditionally (not scoped to `:focus`/`:hover`), and `--destructive-foreground`
is near-white (`oklch(0.985 0 0)`) in both light and dark mode. On the popover's white
background, a destructive item's label is white-on-white and effectively invisible at
rest. The intended hover/focus background (`data-[variant=destructive]:focus:bg-destructive/10`)
would fix contrast when focused, but per the opacity-modifier bug above, `bg-destructive/10`
never compiles either — so the item stays illegible in every state, not just at rest.
Confirmed visually in the DropdownMenu family preview captures (e.g. an "Excluir" row
showing only its icon, no label). Recommend the app team either use `text-destructive`
(a real red, not the near-white foreground) for the resting label, or scope
`text-destructive-foreground` to the same `:focus`/`:hover` state as the background.
Worked around here by dropping `variant="destructive"` from every DropdownMenu-family
preview (`.design-sync/previews/DropdownMenu*.tsx`) so cards show real, legible menu
items instead of reproducing invisible text — previews should demonstrate working states,
not just any state the API technically allows.

**Same bug, same root cause, hits `FormLabel` and `FormMessage` too**: both use
`text-destructive-foreground` for their error state (`form.tsx`'s
`data-[error=true]:text-destructive-foreground` and `FormMessage`'s unconditional
`text-destructive-foreground` class) — same near-white token, same invisible-on-white
result. Confirmed in the `FormLabel`/`FormMessage` preview captures: the "error state"
cells render completely blank where the error label/message text should be. **Not
worked around** — unlike the DropdownMenu case, there's no non-error alternative that
still demonstrates the component's actual purpose (a `FormMessage` with no error is just
absent, per its own `if (!body) return null` — so a "with error" story is the ONLY way to
show it doing anything). Left these two cells graded `needs-work` in
`.design-sync/.cache/review/FormLabel.grade.json` / `FormMessage.grade.json` with a note
pointing here, rather than iterating pointlessly on a preview that's already accurate.
**Actionable for the app team**: any component using `text-destructive-foreground` for
foreground/text (not paired with a `bg-destructive` background) is likely showing
invisible text somewhere in production right now — search
`grep -rn "text-destructive-foreground" components/` for the full list to audit
(`dropdown-menu.tsx`, `form.tsx` confirmed so far; worth checking the rest).

## Real limitation found: Toaster can't demonstrate a toast in an authored preview

`.design-sync/previews/Toaster.tsx` calls `toast.success/error(...)` from the `sonner`
package directly (required — `toast` isn't re-exported from the DS bundle) alongside
`<Toaster />` imported from `salas-reuniao-ui`. Every capture came back blank with zero
page errors. Root cause: the DS bundle (`_ds_bundle.js`) embeds its own bundled copy of
`sonner` for the `Toaster` re-export, while the preview's separate `import { toast } from
"sonner"` resolves to a different bundled copy with its own in-memory store — so
`toast()` succeeds silently but writes to a store the mounted `<Toaster/>` never reads
from. This is an architectural consequence of previews and the DS bundle compiling as
two separate esbuild outputs; fixing it would need `sonner` deduped/aliased to one
resolved module across both bundles (a change to `.ds-sync/lib/preview-rebuild.mjs`'s
bundler config, not something fixable from the preview file). `Toaster` is graded
`needs-work` for this reason — the component itself works fine in the real app, this is
purely a static-preview limitation.

## resync.mjs (the driver) hung twice in this environment; manual sequence used instead

When authoring the conventions header, `node .ds-sync/resync.mjs --config ... --out ./ds-bundle` (no `--remote`, as required for a first sync) hung with zero progress for 18-40+ minutes on two separate attempts, well past where the same work completes in 1-2 minutes via `package-build.mjs` directly. Root cause not diagnosed — possibly Windows-specific (this machine), possibly resource contention from repeated killed node/chromium processes earlier in the same session. Worked around by running the equivalent sequence manually: `package-build.mjs` → `package-validate.mjs` → `package-capture.mjs`, which completed normally each time. This skips the driver's own diff/verdict receipt (`.sync-diff.json` / `.resync-verdict.json`), but the substance (header-bearing build, validated, all previews captured) is equivalent. **On the next re-sync, try `resync.mjs` again first** (this may have been a one-off environment issue) — if it hangs again with no `[DTS]` progress within ~2 minutes, kill it and fall back to the manual sequence; don't assume it's broken forever without retrying.

## cfg.overrides gotcha: adding a `viewport` key requires a full rebuild before ANY scoped rebuild works

Discovered the hard way: `cfg.overrides.<Name>.viewport` is NOT exempt from the grade-key
hash that `preview-rebuild.mjs` uses to decide whether a component's stamped state is
stale (only `cardMode`/`primaryStory` are exempt — see `.ds-sync/lib/sync-hashes.mjs`
`configSlicesFor`). So editing `config.json` to add/change a `viewport` on an override,
then immediately running a *scoped* `preview-rebuild.mjs --components X,Y,Z`, fails with
`[CONFIG_STALE]` for every affected component — it silently does NOT apply to components
without a changed override, only the ones whose override just changed. **Always run one
full unscoped `package-build.mjs` immediately after any `cfg.overrides` edit**, before
attempting any scoped rebuild — this bit multiple parallel authoring batches during this
sync (see git history / commit message for the full incident) purely because overrides
were added incrementally after batches were already mid-flight.

## Sidebar family: override viewport must stay above the 768px mobile breakpoint

`Sidebar`'s `useIsMobile()` hook (`hooks/use-mobile.ts`) treats any viewport narrower
than 768px as mobile, which forces the sidebar into a closed off-canvas `Sheet` (blank
render) unless `collapsible="none"` is set. The `Sidebar`/`SidebarProvider` previews use
`collapsible="none"` deliberately to render reliably at a narrow override viewport; every
other Sidebar-family preview relies on the override viewport being wide enough
(`820x600` — chosen specifically to clear 768px) rather than needing that workaround.
**If you ever narrow these overrides' viewport width below 768px again, every Sidebar
sub-component will render blank** — widen the viewport instead of adding
`collapsible="none"` everywhere.

## Grouping

All 122 exports land under a single `general` group — `components/ui/*.tsx`
files sit flat with no subdirectories, so source-dir-derived grouping has
nothing to key off (`ui` itself is in the converter's generic-dir skip list).
Not fixed — would need per-component `docsMap` stub files with
`category:` frontmatter to regroup, judged not worth the authoring cost for
122 components. Future improvement, not a defect.

## docs/ folder is unrelated

The repo has a `docs/` folder but it holds unrelated business docs (a
"teletrabalho"/remote-work requirements doc), not per-component documentation.
`guidelinesGlob` is explicitly set to `[]` to prevent the default globs
(`docs/*.md` etc.) from picking these up as "design guidelines".

## Known render warns

- The 12 `[RENDER_BLANK]` warnings from the very first validate run
  (BreadcrumbItem, BreadcrumbSeparator, Button, Input, SidebarGroupAction,
  SidebarInput, SidebarMenuAction, SidebarMenuItem, SidebarMenuSubItem,
  TableCell, TableHead, Textarea) were floor-card renders too small to clear
  the 5KB blank-detection threshold — not real bugs. Resolved once each got
  an authored preview with realistic content.
- `[RENDER_THIN]` on `Skeleton` and `Toaster` are expected and permanent —
  both are real bugs/limitations documented above, not something a future
  re-sync should try to "fix" by re-authoring the preview.
- `[GRID_OVERFLOW]` fired for 53 components across this sync (Card family →
  `cardMode: column`; every overlay/portal/compound-family leaf → `cardMode:
  single` with a family-appropriate viewport) — all resolved via
  `cfg.overrides`, see `config.json`. A future re-sync adding NEW components
  to any of these families (Card/Dialog/Drawer/DropdownMenu/Select/Sheet/
  Sidebar/Tooltip) should expect to need the same treatment.

## Re-sync risks

- `.design-sync/compiled-tailwind.css` is machine-generated and gitignored —
  a fresh clone or CI checkout MUST run `cfg.buildCmd` before
  `package-build.mjs`, or the bundle ships unstyled (silently — validate does
  not catch missing CSS content, only missing CSS *files*).
- The `node_modules/salas-reuniao-ui` junction is not committed (node_modules
  is gitignored) — recreate it on every fresh clone/CI runner before running
  the converter (see "Repo shape" above).
- `cfg.pkg`/`cfg.globalName` are synthetic (no real published package) — if
  this repo's real `components/ui` is ever extracted into an actual npm
  package, this config's `srcDir`/junction workaround should be replaced with
  a normal `dist`/`.d.ts` build and `--entry`.
- Grouping is flat (`general`) — a future sync could improve browsability by
  regrouping via `docsMap` stub files, not done here.
- Any `cfg.overrides` edit that adds/changes a `viewport` key needs a full
  unscoped `package-build.mjs` before the next scoped rebuild — see the
  dedicated section above. Easy to forget and get a confusing
  `[CONFIG_STALE]` error.
- The three real upstream app bugs found here (opacity-modified theme-color
  utilities never compile; `text-destructive-foreground` used unconditionally
  in `dropdown-menu.tsx`/`form.tsx`; `Toaster`'s dual-`sonner`-instance issue)
  are independent of design-sync and will still be there next sync unless the
  app team fixes them — re-verify they're still needs-work rather than
  assuming they were fixed.
- 5 components ship with a documented `needs-work` cell and no further fix
  attempted: `Skeleton`, `SidebarMenuSkeleton`, `Toaster`, `FormLabel`,
  `FormMessage`. This was a deliberate stop (real bugs, not preview defects),
  not an oversight — don't treat a `needs-work` grade there as something to
  chase on the next sync.
